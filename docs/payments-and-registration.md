# Платежи и регистрация

## Запуск

После обновления выполните `docker compose up --build`. API накатывает Alembic-миграции перед стартом, существующие пользователи, операции и прогнозы сохраняются. Если запускаете API без Docker: `cd backend`, `uv sync`, `uv run alembic upgrade head`, затем обычная команда запуска.

Старая база, созданная через `create_all` без таблицы `alembic_version`, тоже поддерживается: начальная миграция проверяет существующие таблицы и создаёт недостающие. Старое поле `manual_payment_requests.idempotency_key` переименовывается в `key` с сохранением записей. При несовместимой структуре миграция останавливается с указанием таблицы. PostgreSQL должен пройти проверку готовности перед запуском API, а API — перед запуском nginx.

Nginx обновляет адрес API через Docker DNS: пересоздание контейнера API не требует перезапуска фронтенда. Если API не запустился, причина видна в `docker compose logs api`, а статус готовности — в `docker compose ps`.

В контекст Docker попадают только исходники и файлы сборки. Локальные `.pytest_cache`, `.venv`, `node_modules` и `.env` исключены, чтобы их права доступа не мешали сборке.

## Платежи

- На странице компаний можно создать компанию без выписки. В разделе **Операции → Добавить платёж** вводятся дата, сумма с копейками, контрагент, назначение и фактический остаток на конец дня. ИНН необязателен. Будущие оплаты добавляются через ожидаемые события.
- CSV кейса продолжает работать. TXT должен быть банковской выпиской **1CClientBankExchange** с периодом и остатками; поддерживаются UTF-8, Windows-1251 и DOS CP866. Это отдельный способ загрузки фактических платежей, независимый от интеграции неоплаченных счетов из 1С.
- PDF: поддерживается текстовая рублёвая выписка **Райффайзенбанка** с таблицей операций. Скан, защищённый PDF или иная банковская вёрстка требуют другого адаптера; приложение сообщает об этом. Универсального распознавания произвольных PDF нет.
- Проверяются суммы, контрольные обороты и остатки. Неразобранная выписка не записывается частично. Повторный файл и пересекающиеся банковские периоды не дублируют операции. Один счёт связывается с одной компанией пользователя, чтобы не смешать остатки разных счетов.
- После добавления факта пересчитываются категории, качество данных и сверка план-факт. Категории, изменённые пользователем, сохраняются. Повторная отправка формы с тем же ключом возвращает уже созданный платёж.

Образцы для презентации и тестов находятся в [backend/tests/fixtures](../backend/tests/fixtures/README.md).

## Документы операций

Новый интерфейс находится в `frontend`; отдельная папка `frontend_new` больше не нужна. В подробностях операции можно прикрепить один чек и сопутствующие документы. Новый чек заменяет предыдущий, остальные документы сохраняются. PDF и изображения открываются внутри приложения, остальные форматы можно скачать.

Файлы хранятся в БД вместе с метаданными и входят в её резервные копии. Миграция добавляет таблицу `operation_attachments`, не меняя существующие операции. Доступ к файлам разрешён только владельцу компании. Ограничения: 10 МБ на файл, до 10 файлов за запрос и общий лимит `CASHFLOW_MAX_UPLOAD_MB` (по умолчанию 50 МБ). Поддерживаются PDF, PNG, JPEG, WebP, HEIC, TXT, CSV, XML и офисные документы DOC/DOCX, XLS/XLSX, ODT/ODS.

## Регистрация без подтверждения почты

По решению от 24.10 подтверждение почты исключено из обычной регистрации.
По умолчанию `CASHFLOW_REQUIRE_EMAIL_VERIFICATION=false`, SMTP не требуется.
После перезапуска API можно зарегистрироваться без SMTP; интерфейс сразу выполняет вход с указанными email и паролем.
Ранее созданные неподтверждённые аккаунты тоже могут войти. Повторная регистрация не меняет пароль.
Адрес при этом не отмечается подтверждённым; после возврата настройки в `true` потребуется письмо.
Возврат настройки закрывает новые входы; уже выданные JWT действуют до своего срока (по умолчанию 60 минут).
Старый механизм подтверждения сохранён для совместимости, но включается только явной настройкой `true`.
Вход — по email и паролю; банковского SSO «Центр-инвест» на бэкенде нет.
Основная кнопка интерфейса должна называться «Войти».

Контракт для фронтенда: `GET /api/auth/registration-info` возвращает
`{"email_delivery":"disabled","local_mailbox_url":null}`. В этом режиме форму регистрации
разрешено отправлять; после `POST /api/auth/register` (202, поле `message`) интерфейс
вызывает `/api/auth/login` и переходит к компаниям без ожидания письма.
Регистрация сама не выдаёт JWT. При включённом подтверждении интерфейс показывает
инструкцию и повторную отправку письма, а ссылка `/verify-email` остаётся рабочей.

## Проверка регистрации с подтверждением локально

Сначала установите `CASHFLOW_REQUIRE_EMAIL_VERIFICATION=true` и перезапустите API.

1. Откройте приложение на `http://localhost:5173`, нажмите **Зарегистрироваться**.
2. Введите email и пароль от 8 символов. До подтверждения вход закрыт.
3. Откройте **Mailpit** на `http://localhost:8025`: письмо будет там, на реальный адрес оно не отправляется. Перейдите по ссылке и нажмите **Подтвердить email**.
4. Войдите с email и паролем. Существующие логины, включая демо-пользователя, работают как раньше.

Ссылка одноразовая, по умолчанию действует 60 минут. Новое письмо можно запросить на странице `/register?resend=1` через минуту; новая ссылка отменяет старую. Открытие страницы само по себе не подтверждает email: подтверждение выполняется кнопкой. При недоступной почте API возвращает ошибку отправки.

Для запуска API вне Docker можно оставить Mailpit в контейнере (`docker compose up -d mailpit`) и задать в `backend/.env`:

```dotenv
CASHFLOW_SMTP_HOST=127.0.0.1
CASHFLOW_SMTP_PORT=1025
CASHFLOW_SMTP_SECURITY=none
CASHFLOW_SMTP_FROM=no-reply@ledokol.local
CASHFLOW_PUBLIC_APP_URL=http://localhost:5173
```

## Что нужно для реальных писем

Подключите SMTP у вашего почтового провайдера. Запишите параметры в **backend/.env** (этот файл не коммитится):

```dotenv
CASHFLOW_PUBLIC_APP_URL=https://ваш-домен-приложения
CASHFLOW_SMTP_HOST=smtp.ваш-провайдер
CASHFLOW_SMTP_PORT=587
CASHFLOW_SMTP_SECURITY=starttls
CASHFLOW_SMTP_USER=ваш-логин
CASHFLOW_SMTP_PASSWORD=пароль-приложения-или-SMTP-ключ
CASHFLOW_SMTP_FROM=no-reply@ваш-домен
CASHFLOW_VERIFICATION_TTL_MINUTES=60
```

Для порта 465 укажите `CASHFLOW_SMTP_SECURITY=ssl`. Подтвердите адрес отправителя или домен у провайдера; настройте DNS-записи SPF/DKIM и DMARC по его инструкции. `CASHFLOW_PUBLIC_APP_URL` должен открываться с устройства получателя; `localhost` подходит только для локальной проверки. После изменения настроек пересоздайте API: `docker compose up -d --force-recreate api`.

SMTP-настройки из `backend/.env` перекрывают локальные значения из `backend/mailpit.env`. Mailpit можно оставить для разработки. Для нескольких процессов API ограничение попыток следует вынести из памяти процесса в общее хранилище.

Страница регистрации проверяет режим доставки через `/api/auth/registration-info`. Без настроенного SMTP она объясняет, что отправка ещё не подключена; для Mailpit показывает ссылку на тестовый ящик. Это проверка конфигурации, а не гарантия доступности SMTP или попадания письма во входящие. При переходе на реального провайдера задайте `CASHFLOW_LOCAL_MAILBOX_URL=` в `.env`; в режиме prod локальная ссылка не публикуется. Логин, пароль SMTP и ссылки подтверждения этот эндпоинт не возвращает.

## Слои

`domain/statements.py` проверяет банковские остатки без БД и библиотек PDF. `importers/` преобразует внешние форматы в эту модель. Сервисы `statements`, `payments`, `history` выполняют транзакции и общую обработку истории. Регистрация зависит от порта `VerificationMailer`; SMTP находится в `integrations/email.py`. Роуты проверяют входные данные и владение, интерфейс вызывает API.
